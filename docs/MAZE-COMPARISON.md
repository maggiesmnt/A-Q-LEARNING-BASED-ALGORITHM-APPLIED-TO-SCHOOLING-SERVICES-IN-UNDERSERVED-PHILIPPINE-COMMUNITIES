# Maze Comparison

Maze Comparison is a live, paired simulation of Standard Q-Learning and the
Enhanced Multi-Objective Double Q-Learning (MODQL) policy. The outputs are
computed from simulation runs; the page does not preload comparison metrics.
The simulation is not field evidence and does not establish an overall winning
algorithm.

## Scenarios and controls

The page has four fixed-seed scenarios, selected in the global header:

1. **Basic Grid** — one agent and one target on a plain grid.
2. **Obstacles** — one agent and one target in a fixed maze-like layout with
   alternating corridor bottlenecks and dead-end pockets.
3. **Multi-Target** — one agent and six targets with a fixed seed-303 obstacle
   map shared by training and evaluation.
4. **Laiban Case** — the Laiban application, using the saved ALS Hub and nine-sitio schematic,
   learner allocation, previous-visit counts, visit recency, closed roads,
   simulated 38 mm/24h rainfall, a 480-minute shift and 60-minute service stops.

Both policies share a single environment, start location, destinations,
obstacles, seed, and training episode for each paired rollout. Tab 4's saved
road closures are preserved. Its additional temporary obstacle is explicitly
a simulated overlay and is applied only to open road cells. The sitio-level
learner allocation and visit history remain labeled simulated, not verified
field data.

Policies are pre-generated by `node scripts/generate-maze-policies.js`, with
5,000 episodes per policy, alpha 0.10, gamma 0.90, epsilon starting at 1.00,
a 0.995 per-episode decay, and a 0.05 minimum. Each scenario JSON stores the
trained Q tables, training metadata, and the per-episode training log only; it
contains no evaluation results or metrics. Opening a scenario loads its policy
without retraining. Tab 2 uses the same fixed maze in training and evaluation;
each paired training episode draws one seeded start from the 56 open,
non-target cells for both policies. The interactive demo still starts at
`(0,0)`. Starting a comparison immediately begins a fresh, frozen
evaluation. **Retrain from scratch** runs both policies in a Web Worker using
typed-array Q tables and no rendering during training, with episode progress
shown in the page. Reset clears only the displayed run and preserves the
loaded policy. Advance One Step and the speed and travel-time-unit selectors
operate on the active scenario. Shared-tick and obstacle-update counts appear
only for dynamic-obstacle scenarios.

The Tab 2 batch keeps the maze, target, demand, service budget, policy
parameters, and paired Standard/MODQL conditions fixed. It cycles the start
location through the same 56 open, non-target cells in row-major order for 200
paired evaluations (three full cycles plus 32 additional starts). Only the
start location varies; both policies share each start and the default
interactive run remains `(0,0)`.

The hand-defined 10×10 maze uses alternating horizontal corridors separated
by single-cell bottlenecks, with two one-exit pockets at `(9,2)` and `(9,5)`.
Its ten rows are:

```
..........
#########.
..........
.#########
..........
#########.
..........
.#########
..........
##.##.###.
```

There are 43 blocked cells and 56 open non-target starts; all 56 can reach the
target at `(9,9)`. A breadth-first search gives a shortest route of 54 moves
from `(0,0)`, versus Manhattan distance 18 (3× as long). In the generated
policy's final 500 training episodes, Standard reached the target 497 times
(99.4%) and MODQL 500 times (100%). The batch completed 200/200 runs for each
policy, with zero loop detections or other failures. Both had mean 28.66
movement steps and population SD 15.51. The 54-move route is the default-start
shortest path; the batch averages include all 56 start cells. These are
simulated, frozen-policy results, not a tuned or guaranteed ranking.

These results replace batch results from the earlier, easier Tab 2 map; the
maze layout was changed without altering training parameters, reward/state
definitions, or the algorithms.

The former browser loop trained only five episodes per task and redrew both
grids and their details after every chunk. Training also repeated weighted
shortest-path searches and rebuilt the same MODQL state strings. Training now
runs off-thread with no grid rendering, grows Q rows in typed arrays, caches
travel estimates per obstacle layout, and reuses MODQL state encodings within
an episode. A measured 5,000-episode Laiban training run fell from about 40
seconds before optimization to about 16 seconds in the same Node environment;
the browser remains responsive while the Worker reports progress.

## Tab 3 diagnosis and fixed-map follow-up

The initial diagnostic below describes Tab 3 with obstacles changing every 20
shared ticks. After reviewing those results, the user approved freezing the
seed-303 initial obstacle layout for both training and evaluation. The
algorithm, reward, state, parameters, and 5,000-episode budget were not changed.

The implementation and tests confirm two distinct agents. Standard uses its
single `q` table: the state key is only `row,column`, `values()` reads `q`,
training action selection is epsilon-greedy over legal moves, and evaluation
is greedy. Its service reward is one scalar; a normal move gets zero. MODQL
selects actions epsilon-greedily from `Q1 + Q2`; on each learning update it
chooses Q1 or Q2 with probability 0.5, selects the next action with that table,
and evaluates it with the other table. Frozen evaluation greedily chooses
using `Q1 + Q2`. The unit tests cover Standard's location-only state and
epsilon-greedy exploration, MODQL's summed-table action choice and Double-Q
update, and frozen evaluation without Q updates.

MODQL encodes the six sites in config order A–F. The fixed site locations and
their initial demand/history buckets are:

| Site | Position | Demand | D bucket | H bucket |
|---|---:|---:|---:|---:|
| A | (1,8) | 18 | 1 | 1 |
| B | (3,2) | 30 | 2 | 1 |
| C | (5,8) | 22 | 2 | 1 |
| D | (7,1) | 28 | 2 | 1 |
| E | (8,8) | 16 | 1 | 1 |
| F | (2,5) | 24 | 2 | 1 |

For the first held-out rollout, the MODQL tuples were:

- Start: `L=0,0|D=122212|T=1|H=111111|A=111111`.
- Immediately after serving B at `(3,2)`: `L=3,2|D=102212|T=1|H=101111|A=101111`.
- At the first two-cell loop, at C `(5,8)`: `L=5,8|D=000210|T=0|H=000110|A=000110`; the alternating cell `(6,8)` had the same `D/T/H/A` fields.

Each character in D, H, and A corresponds to A–F, including sites already
served (encoded as `0`). A is current reachability, not an instruction or
direction. The state contains no site coordinates or direction-to-site
mapping: positions are fixed in the scenario configuration, while the
agent's movement action remains Up, Down, Left, or Right. The Chapter 4 thesis
text is not present in this repository, so its action granularity cannot be
verified here; only the current browser implementation's four-direction
action model is source-verifiable.

Training was reproduced for the configured 5,000 episodes. In the last 500,
Standard completed all six sites in 0 episodes and served a mean 1.026 targets
per episode; MODQL completed all six in 6 episodes and served a mean 2.938.
Across the training action choices, Standard visited 97 distinct location
states and MODQL visited 6,470 distinct encoded states. Both rewards are
sparse: a normal move yields 0; target service yields a positive reward. The
observed service rewards were 0.5505–15.0000 for Standard and
0.2003–0.7320 for MODQL.

The frozen 200-run Tab 3 evaluation completed all sites 0/200 times for
Standard and 3/200 for MODQL. The loop detector flagged Standard 200/200 times
and MODQL 198/200 times; there were no runs with neither completion nor a loop
flag. One MODQL completion also had a detected loop (197 loop-only failures,
2 completions without a loop, and 1 completion after a loop).

Representative greedy loop Q values below are in Up, Down, Left, Right order;
the spread is max minus second-max among legal actions. MODQL values are Q1 +
Q2:

| Policy/cell | Encoded state | Legal moves | Q values | Greedy move | Legal spread |
|---|---|---|---|---|---:|
| Standard `(3,1)` | `3,1` | Up, Down, Left, Right | `[0.5782, 0.5615, 0.5658, 1.1533]` | Right | 0.5752 |
| Standard `(3,2)` | `3,2` | Down, Left, Right | `[0.9418, 0.5982, 1.0809, 0.7921]` | Left | 0.2888 |
| MODQL `(5,8)` | `L=5,8|D=000210|T=0|H=000110|A=000110` | Up, Down | `[0.0344, 0.2359, 0.0264, 0.0177]` | Down | 0.2015 |
| MODQL `(6,8)` | `L=6,8|D=000210|T=0|H=000110|A=000110` | Up, Left | `[0.1942, 0.7854, 0.1866, 0.1781]` | Up | 0.0076 |

The policies alternate between `(3,1)`/`(3,2)` for Standard and `(5,8)`/`(6,8)`
for MODQL. MODQL's state changes when sites are served and when the time bucket
or accessibility changes; it is unchanged across this particular loop because
the same destinations remain served, T stays at 0, and the reachability bits
stay constant.

In the original dynamic version, Tab 3 changed the grid obstacle layout every
20 shared movement ticks during both training and evaluation. Each grid update toggled one to three cells.
Training made 25,199 updates and 50,282 cell toggles across 5,000 episodes
(5.04 updates and 10.06 toggles per episode); every episode had at least one
update. The 200 evaluations made 1,028 updates and 2,054 cell toggles
(5.14 updates and 10.27 toggles per run). Training seeds are
`303 + 1000 + episode*7919`; evaluation seeds are
`303 + 100000 + index*7919`, so obstacle sequences are not the same. A fixed
layout shared by training and evaluation would make transitions stationary
and remove that sequence mismatch, which should make convergence more
plausible; it cannot guarantee convergence, particularly with sparse rewards
and Standard's location-only state.

### Results after freezing the Tab 3 map

The fixed layout is the seed-303 sample from the prior 24%-obstacle generator,
stored explicitly in `maze-scenarios.js`. It has 24 obstacle cells, every site
is reachable from `(0,0)`, and obstacle updates are disabled. The offline
script regenerated `policies/tab-3.json` using the existing training budget
and parameters.

In the last 500 training episodes, Standard completed all six sites 0 times
and served a mean 1.494 sites per episode. MODQL completed all six 498 times
and served a mean 5.996 sites; across all 5,000 episodes it completed 4,096.
The agents visited 74 distinct Standard location states and 734 MODQL encoded
states during training.

On the frozen 200-run batch, Standard completed 0 runs, triggered the loop
detector in 200, and served a mean of 1 site in 110 moves (SD 0). MODQL
completed 200/200 runs, served all 6 sites in 49 moves (SD 0), and had no
loop detections or other failures. Standard's representative loop is
`(2,2)` ↔ `(3,2)`: its greedy moves are Down and Up, with legal-action Q
spreads 0.1191 and 0.0651 respectively. MODQL did not loop. Thus, with this
fixed map and unchanged learner definitions, MODQL's training and evaluation
converged on the six-site task while Standard still did not. This is a
scenario-specific simulated result, not a general convergence guarantee.

## Policy and environment behavior

Both policies act using the same four cardinal movement actions. Walls,
obstacles, closed cells, and grid boundaries are the only movement constraints.
The Standard agent's Q-table key is its current grid location only. Its action
selection uses only the legal four-direction moves at that location; these
shared constraints reflect grid boundaries and blocked cells, not target
feasibility. It does not use demand, remaining time, visit history,
accessibility, a goal-position variable, a shared route planner, or a
shortest-path helper in its policy state or action selection. A service event
supplies the ordinary scalar reward when a target is reached. Those environment
values may also be displayed as measurements. Standard uses epsilon-greedy
exploration while training and a greedy, frozen policy during evaluation.
Time-budget and movement-limit terminations truncate Standard training
episodes without creating a time-dependent Q update.
Both side panels display demand, visit history, remaining time and current
reachability as environmental measurements. The Standard panel explicitly
labels them as display-only; they are not encoded in its Q state or update.

MODQL maintains Q1 and Q2. A random estimator is used for action selection in
each Double-Q update, and the other estimator evaluates that action. Its state
includes location, per-sitio demand buckets, remaining-time bucket, visit
history buckets, and two-level current accessibility (reachable or
unreachable). The final evaluation policy is greedy on the combined Q1 and Q2
values. This grid representation simplifies roads to open/blocked cells and
does not distinguish the operational open, caution, and restricted bands.

MODQL's service reward is calculated from the selected site's demand relative
to the maximum site demand, Jain fairness after the candidate service is
projected, and travel-time efficiency. Its travel-time term uses the weighted
grid travel-time estimate to the candidate computed at the start of that
service leg. Standard receives one scalar travel-time reward. The reward
scales are different and are not compared as performance scores.

Every evaluation result is computed from its actual rollout: learners served
and coverage, Jain fairness, travel minutes, movement steps, destinations
served, deferred communities, completion state, and Q diagnostics. Before a
run starts, results display “Not run yet.” The assessment describes metric
differences and trade-offs; it does not produce an overall score or claims
beyond the selected simulated scenario.

The separate batch panel evaluates both frozen policies over 200 paired
scenarios and calculates a mean and population standard deviation for each
reported outcome metric. Other scenario batches use held-out seeds; Tab 2 uses
the fixed-map start-position protocol above. Loop rate reports the fraction of
rollouts that repeat a two-cell cycle for at least four complete cycles without
serving a destination. Basic Grid fairness is trivial because there is one
destination. The prototype's batch results are not comparable to Chapter 4
results.

The training curves below the agent grids show the actual per-episode step
counts recorded during policy training. The JSON files also retain per-episode
reward logs for reproducibility.

Frozen greedy action ties are resolved by taking the first legal action in the
fixed Up, Down, Left, Right order. Unseen state rows have all-zero values for
both algorithms, so they use the same tie rule.

## SOP selector

The SOP questions and titles reuse the established Maze Comparison wording.
Objective statements are centralized in `maze-scenarios.js` and remain marked
“Objective wording pending”; no new thesis objectives are invented. The
selector presents the existing limitation, MODQL's corresponding approach,
and highlights the applicable result rows. Q-estimator differences and
estimated-return gaps are diagnostics only, not proof that overestimation bias
was reduced.

## Python baseline compatibility

The repository's `simple_maze_demo.py` imports `dynamic_maze_env.py`,
`baseline_confidence_agent.py`, and `reflection_agent.py`; those dependencies
are not present in the repository. The plain-grid tab implements the requested
single-agent, single-target Standard-Q baseline conditions in the browser, but
the exact Python program could not be executed or verified against this
simulation. The separate `maze-legacy.js` browser baseline is not substituted
for those missing Python sources.
