# Maze Comparison

Maze Comparison is a live, paired simulation of Standard Q-Learning and the
Enhanced Multi-Objective Double Q-Learning (MODQL) policy. The outputs are
computed from simulation runs; the page does not preload comparison metrics.
The simulation is not field evidence and does not establish an overall winning
algorithm.

## Scenarios and controls

The page has four fixed-seed scenarios, selected in the global header:

1. **Basic Grid** — one agent and one target on a plain grid.
2. **Obstacles** — one agent and one target with one fixed set of 24 static
   obstacles.
3. **Multi-Target** — one agent and multiple targets with obstacles that may
   change every 20 shared ticks.
4. **Laiban Case** — the Laiban application, using the saved ALS Hub and nine-sitio schematic,
   learner allocation, previous-visit counts, visit recency, closed roads,
   simulated 38 mm/24h rainfall, a 480-minute shift and 60-minute service stops.

Both policies share a single environment, start location, destinations,
obstacles, seed, and training episode for each paired rollout. Tab 4's saved
road closures are preserved. Its additional temporary obstacle is explicitly
a simulated overlay and is applied only to open road cells. The sitio-level
learner allocation and visit history remain labeled simulated, not verified
field data.

Policies are pre-generated by `node scripts/generate-maze-policies.js`, with
5,000 episodes per policy, alpha 0.10, gamma 0.90, epsilon starting at 1.00,
a 0.995 per-episode decay, and a 0.05 minimum. Each scenario JSON stores the
trained Q tables, training metadata, and the per-episode training log only; it
contains no evaluation results or metrics. Opening a scenario loads its policy
without retraining. Tab 2 uses the same fixed obstacle coordinates in all
training episodes and the default single-run evaluation; only training action
choices vary. Starting a comparison immediately begins a fresh, frozen
evaluation. **Retrain from scratch** runs both policies in a Web Worker using
typed-array Q tables and no rendering during training, with episode progress
shown in the page. Reset clears only the displayed run and preserves the
loaded policy. Advance One Step and the speed and travel-time-unit selectors
operate on the active scenario. Shared-tick and obstacle-update counts appear
only for dynamic-obstacle scenarios.

The Tab 2 batch keeps its obstacle coordinates, target, demand, service budget,
policy parameters, and paired Standard/MODQL conditions fixed. To provide 200
distinct held-out runs despite the fixed map and deterministic evaluation tie
breaks, it cycles the start location through the 75 open, non-target cells in
row-major order; those 75 locations are used repeatedly to make 200 runs.
Both agents share each sampled start. No obstacle layout or policy tie-break
is randomized in this batch.

The former browser loop trained only five episodes per task and redrew both
grids and their details after every chunk. Training also repeated weighted
shortest-path searches and rebuilt the same MODQL state strings. Training now
runs off-thread with no grid rendering, grows Q rows in typed arrays, caches
travel estimates per obstacle layout, and reuses MODQL state encodings within
an episode. A measured 5,000-episode Laiban training run fell from about 40
seconds before optimization to about 16 seconds in the same Node environment;
the browser remains responsive while the Worker reports progress.

## Policy and environment behavior

Both policies act using the same four cardinal movement actions. Walls,
obstacles, closed cells, and grid boundaries are the only movement constraints.
The Standard agent's Q-table key is its current grid location only. Its action
selection uses only the legal four-direction moves at that location; these
shared constraints reflect grid boundaries and blocked cells, not target
feasibility. It does not use demand, remaining time, visit history,
accessibility, a goal-position variable, a shared route planner, or a
shortest-path helper in its policy state or action selection. A service event
supplies the ordinary scalar reward when a target is reached. Those environment
values may also be displayed as measurements. Standard uses epsilon-greedy
exploration while training and a greedy, frozen policy during evaluation.
Time-budget and movement-limit terminations truncate Standard training
episodes without creating a time-dependent Q update.
Both side panels display demand, visit history, remaining time and current
reachability as environmental measurements. The Standard panel explicitly
labels them as display-only; they are not encoded in its Q state or update.

MODQL maintains Q1 and Q2. A random estimator is used for action selection in
each Double-Q update, and the other estimator evaluates that action. Its state
includes location, per-sitio demand buckets, remaining-time bucket, visit
history buckets, and two-level current accessibility (reachable or
unreachable). The final evaluation policy is greedy on the combined Q1 and Q2
values. This grid representation simplifies roads to open/blocked cells and
does not distinguish the operational open, caution, and restricted bands.

MODQL's service reward is calculated from the selected site's demand relative
to the maximum site demand, Jain fairness after the candidate service is
projected, and travel-time efficiency. Its travel-time term uses the weighted
grid travel-time estimate to the candidate computed at the start of that
service leg. Standard receives one scalar travel-time reward. The reward
scales are different and are not compared as performance scores.

Every evaluation result is computed from its actual rollout: learners served
and coverage, Jain fairness, travel minutes, movement steps, destinations
served, deferred communities, completion state, and Q diagnostics. Before a
run starts, results display “Not run yet.” The assessment describes metric
differences and trade-offs; it does not produce an overall score or claims
beyond the selected simulated scenario.

The separate batch panel evaluates both frozen policies over 200 paired
scenarios and calculates a mean and population standard deviation for each
reported outcome metric. Other scenario batches use held-out seeds; Tab 2 uses
the fixed-map start-position protocol above. Loop rate reports the fraction of
rollouts that repeat a two-cell cycle for at least four complete cycles without
serving a destination. Basic Grid fairness is trivial because there is one
destination. The prototype's batch results are not comparable to Chapter 4
results.

The training curves below the agent grids show the actual per-episode step
counts recorded during policy training. The JSON files also retain per-episode
reward logs for reproducibility.

Frozen greedy action ties are resolved by taking the first legal action in the
fixed Up, Down, Left, Right order. Unseen state rows have all-zero values for
both algorithms, so they use the same tie rule.

For the fixed Tab 2 map, the default start-to-target route succeeds for both
policies. In the 200-start-position batch, Standard completed 191 runs (95.5%)
and MODQL completed 153 (76.5%). Their loop rates were 6/200 (3.0%) and
50/200 (25.0%); each had three other failures. These are computed simulation
outcomes, not a tuned or guaranteed ranking. In the final 500 training
episodes, both policies reached the target in 500/500 episodes.

## SOP selector

The SOP questions and titles reuse the established Maze Comparison wording.
Objective statements are centralized in `maze-scenarios.js` and remain marked
“Objective wording pending”; no new thesis objectives are invented. The
selector presents the existing limitation, MODQL's corresponding approach,
and highlights the applicable result rows. Q-estimator differences and
estimated-return gaps are diagnostics only, not proof that overestimation bias
was reduced.

## Python baseline compatibility

The repository's `simple_maze_demo.py` imports `dynamic_maze_env.py`,
`baseline_confidence_agent.py`, and `reflection_agent.py`; those dependencies
are not present in the repository. The plain-grid tab implements the requested
single-agent, single-target Standard-Q baseline conditions in the browser, but
the exact Python program could not be executed or verified against this
simulation. The separate `maze-legacy.js` browser baseline is not substituted
for those missing Python sources.
