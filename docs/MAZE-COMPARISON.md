# Maze Comparison

Maze Comparison is a live, paired simulation of Standard Q-Learning and the
Enhanced Multi-Objective Double Q-Learning (MODQL) policy. The outputs are
computed from simulation runs; the page does not preload comparison metrics.
The simulation is not field evidence and does not establish an overall winning
algorithm.

Each algorithm card contains the full 14-row results table: Metric (including
its preference hint), that policy's value, and the live metric-by-metric
assessment. The metric table sits on the left; the grid, trained details, run
status and training log sit on the right. Every metric row is visible, and the
collapsed Policy inputs section remains below the card body. Both cards bind
values to the existing live evaluation records and comparison formatter.
Before a run (and after reset), values read “Not run yet”; after a run, each
card shows only its own policy's metrics. No separate comparative-results
table is repeated below the cards; a short run assessment note remains.

## Scenarios and controls

The page has four fixed-seed scenarios, selected in the global header:

1. **Basic Grid** — one agent and one target on a plain grid.
2. **Obstacles** — one agent and one target in a fixed layout of randomly
   placed obstacle blocks, with multiple routes to the target.
3. **Multi-Target** — one agent and six targets with a fixed seed-303 obstacle
   map shared by training and evaluation.
4. **Laiban Case** — the fixed 10×10 reference grid, orange start at `(0,0)`,
   nine table-backed sitios, a 480-minute shift and 60-minute service stops.

Both policies share a single environment, start location, destinations,
obstacles, seed, and training episode for each paired rollout. Tab 4 training,
evaluation, reachability, marker labels, and result metrics all use its fixed
10×10 grid and the same nine sitio records displayed in the table. The
learner allocation and visit history remain labeled simulated, not verified
field data. The Tab 4 grid has one disconnected open sitio; the current
reachability and trained-run results are documented in the Tab 4 section below.

Policies are pre-generated by `node scripts/generate-maze-policies.js`, with
5,000 episodes per policy, alpha 0.10, gamma 0.90, epsilon starting at 1.00,
a 0.995 per-episode decay, and a 0.05 minimum. Each scenario JSON stores the
trained Q tables, training metadata, and the per-episode training log only; it
contains no evaluation results or metrics. Opening a scenario loads its policy
without retraining. Training logs record actual steps and rewards per episode;
Tab 2 and Tab 4 logs also record whether each episode served all reachable
destinations. Tab 2 uses the same fixed maze in training and evaluation; each
paired training episode draws one seeded start from the 67 open,
non-target cells for both policies. The interactive demo still starts at
`(0,0)`. Starting a comparison immediately begins a fresh, frozen
evaluation. **Retrain from scratch** runs both policies in a Web Worker using
typed-array Q tables and no rendering during training, with episode progress
shown in the page. Reset clears only the displayed run and preserves the
loaded policy. Advance One Step and the simulation-speed selector operate on
the active scenario. The removed travel-time-unit selector has no effect on
simulation calculations; travel time is always displayed in minutes and
movement steps are reported separately. Shared-tick and obstacle-update
counts appear only for dynamic-obstacle scenarios.

The Tab 2 batch keeps the map, target, demand, service budget, policy
parameters, and paired Standard/MODQL conditions fixed. It cycles the start
location through the same 67 open, non-target cells in row-major order for 200
paired evaluations (two full cycles plus 66 starts in a third cycle). Only the
start location varies; both policies share each start and the default
interactive run remains `(0,0)`. Training starts are independently sampled
from the same 67 cells using the same seeded sequence for both learners.

The hand-defined 10×10 layout has 32 blocked cells (32% density), a mix of
individual blocks and short 2–3-cell segments, and no full-width wall. Its
rows are:

```
........#.
#......##.
..#..#..#.
.#.##.....
#...#.##..
#.#....#.#
....##.#..
##...##.##
.#.#.....#
....##....
```

All 67 open non-target starts can reach the target at `(9,9)`. A breadth-first
search gives a shortest route of 24 moves from `(0,0)`, versus Manhattan
distance 18 (1.33× as long), with multiple shortest paths. In the generated
policy's final 500 training episodes, Standard reached the target 493 times
(98.6%) and MODQL 500 times (100%). The frozen 200-start batch completed
200/200 runs for both, with no loop detections or other failures. Standard
averaged 14.665 moves (population SD 6.355); MODQL averaged 14.575 (SD 6.118).
These are simulated, frozen-policy results, not a tuned or guaranteed ranking.

These results replace batch results from the earlier, easier Tab 2 map; the
maze layout was changed without altering training parameters, reward/state
definitions, or the algorithms.

The former browser loop trained only five episodes per task and redrew both
grids and their details after every chunk. Training also repeated weighted
shortest-path searches and rebuilt the same MODQL state strings. Training now
runs off-thread with no grid rendering, grows Q rows in typed arrays, caches
travel estimates per obstacle layout, and reuses MODQL state encodings within
an episode. A measured 5,000-episode Laiban training run fell from about 40
seconds before optimization to about 16 seconds in the same Node environment;
the browser remains responsive while the Worker reports progress.

## Tab 3 diagnosis and fixed-map follow-up

The initial diagnostic below describes Tab 3 with obstacles changing every 20
shared ticks. After reviewing those results, the user approved freezing the
seed-303 initial obstacle layout for both training and evaluation. The
algorithm, reward, state, parameters, and 5,000-episode budget were not changed.

The implementation and tests confirm two distinct agents. Standard uses its
single `q` table: the state key is only `row,column`, `values()` reads `q`,
training action selection is epsilon-greedy over legal moves, and evaluation
is greedy. Its service reward is one scalar; a normal move gets zero. MODQL
selects actions epsilon-greedily from `Q1 + Q2`; on each learning update it
chooses Q1 or Q2 with probability 0.5, selects the next action with that table,
and evaluates it with the other table. Frozen evaluation greedily chooses
using `Q1 + Q2`. The unit tests cover Standard's location-only state and
epsilon-greedy exploration, MODQL's summed-table action choice and Double-Q
update, and frozen evaluation without Q updates.

## Policy and environment behavior

Both policies act using the same four cardinal movement actions. Walls,
obstacles, closed cells, and grid boundaries are the only movement constraints.
The Standard agent's Q-table key is its current grid location only. Its action
selection uses only the legal four-direction moves at that location; these
shared constraints reflect grid boundaries and blocked cells, not target
feasibility. It does not use demand, remaining time, visit history,
accessibility, a goal-position variable, a shared route planner, or a
shortest-path helper in its policy state or action selection. A service event
supplies the ordinary scalar reward when a target is reached. Those environment
values may also be displayed as measurements. Standard uses epsilon-greedy
exploration while training and a greedy, frozen policy during evaluation.
Time-budget and movement-limit terminations truncate Standard training
episodes without creating a time-dependent Q update.
Both side panels display demand, visit history, remaining time and current
reachability as environmental measurements. The Standard panel explicitly
labels them as display-only; they are not encoded in its Q state or update.

MODQL maintains Q1 and Q2. A random estimator is used for action selection in
each Double-Q update, and the other estimator evaluates that action. Its state
includes location, per-sitio demand buckets, remaining-time bucket, visit
history buckets, and two-level current accessibility (reachable or
unreachable). The final evaluation policy is greedy on the combined Q1 and Q2
values. The Laiban map visualizes operational open, caution and restricted
bands, but MODQL's state retains only two-level reachability; it does not
encode those granular band labels.

MODQL's service reward is calculated from the selected site's demand relative
to the maximum site demand, Jain fairness after the candidate service is
projected, and travel-time efficiency. Its travel-time term uses the weighted
grid travel-time estimate to the candidate computed at the start of that
service leg. Standard receives one scalar travel-time reward. The reward
scales are different and are not compared as performance scores.

Every evaluation result is computed from its actual rollout: learners served
and coverage, Jain fairness, travel time (minutes), movement steps,
destinations served, deferred communities, completion state, and Q diagnostics.
Those values appear within their respective cards; the separate table below
contains the metric name and assessment only. Before a run starts, each card
metric and assessment reads “Not run yet.” The assessment describes metric
differences and trade-offs; travel time is reported in minutes and movement
steps are a separate metric. It does not produce an overall score or claims
beyond the selected simulated scenario.

The separate batch panel evaluates both frozen policies over 200 paired
scenarios and calculates a mean and population standard deviation for each
reported outcome metric. Other scenario batches use held-out seeds; Tab 2 uses
the fixed-map start-position protocol above. Loop rate reports the fraction of
rollouts whose final nine trail positions alternate between the same two
adjacent cells (four complete round trips) with no service in those eight
moves. The detector is display/measurement-only: it does not affect action
selection, updates or termination. It examines only the current trail suffix,
so a policy that later moves to a new cell clears the live loop label; normal
backtracking through a corridor is not a loop. The Tab 3 route audit confirms
every recorded move is cardinally adjacent and every destination is open when
used; the canvas joins adjacent cell centers and does not route through walls.
Basic Grid fairness is trivial because there is one destination. The
prototype's batch results are not comparable to Chapter 4 results.

The training curves below the agent grids show the actual per-episode step
counts recorded during policy training. The JSON files also retain per-episode
reward logs for reproducibility; Tab 2 and Tab 4 additionally store per-episode
reachable-completion booleans so their training success rates can be reported
without inferring success from reward.

Frozen greedy action ties are resolved by taking the first legal action in the
fixed Up, Down, Left, Right order. Unseen state rows have all-zero values for
both algorithms, so they use the same tie rule.

## SOP selector

The SOP questions and titles reuse the established Maze Comparison wording.
Objective statements are centralized in `maze-scenarios.js` and remain marked
“Objective wording pending”; no new thesis objectives are invented. The

## Map sensitivity (offline analysis)

This offline experiment measures sensitivity to additional fixed obstacle
maps; it is not part of the live comparison, and it does not change the
default maps, UI, or saved policies. Reproduce it with
`node scripts/run-maze-map-sensitivity.js`. Each map trains fresh Standard and
MODQL policies for 5,000 paired episodes using the unchanged alpha 0.10,
gamma 0.90, epsilon 1.00→0.05, and 0.995 decay. Standard and MODQL share each
episode's environment and (for Tab 2) the same seeded training-start sequence.
Each trained pair is evaluated in a separate frozen 200-run batch.

Maps are generated in memory by the existing seeded `World.generateObstacles`
rule, sampling without replacement from cells other than the start and target
sites. Tab 2 samples exactly 32 cells (32% density); a map is accepted only if
all 67 open non-target cells can reach the target. Tab 3 samples exactly 24
cells (24% density); a map is accepted only if all six targets are reachable
from `(0,0)` and no connectivity repair changes the density. Candidate seeds
are scanned from 2203 for Tab 2 and 3304 for Tab 3; the first five distinct
maps satisfying those structural conditions are used. The accepted Tab 2
seeds are 2261, 2265, 2313, 2323, and 2350; the accepted Tab 3 seeds are 3305
through 3309. Acceptance depends only on density and reachability, not policy
outcomes.

Tab 2 preserves the existing seeded random-start training over its 67 open
non-target cells; the 200 evaluation runs cycle those same cells in row-major
order. Tab 3 preserves its existing fixed `(0,0)` start for both training and
evaluation. No dynamic obstacles are used. Per-map completion and loop values
are percentages of 200 runs; loop counts use the current trailing two-cell
cycle detector. Targets served, coverage, Jain fairness, and travel time are
means across the 200 runs. Overall means and population SDs below are computed
across the five per-map means, giving each map equal weight. Tab 2's Jain
fairness is 1.000 on every map and is not informative for a one-destination
